# PoC：CRシート整合チェック（v0）＋ 提出画像OCR照合（v1）

設計思想（**AIに判断させず機械照合する**）が実データで動くことを示す実証コードです。

- `cr_check.py` … **v0**：提出物が無くても検証できる「CRシート単体の整合チェック」
- `ocr_match.py` … **v1**：提出画像をOCRしてCRシートの正解と照合

- 考え方：[../docs/AIレビューの仕組み_設計書_チーム共有用.md](../docs/AIレビューの仕組み_設計書_チーム共有用.md)
- 仕様：[../docs/照合ロジック仕様_たたき台.md](../docs/照合ロジック仕様_たたき台.md)

## v0（CRシート単体）— `cr_check.py`

### できること

1. **色番号↔色ライン名の整合**（シート全体）
   同じ色番号が別のライン名で書かれていないか＝取り違え/誤記を検出。
2. **キャプション使用色 ⊆（文字入れ指示 ∪ 対象商材）**（投稿単位）
   キャプションにあるのにシートのどこにも無い色番号＝キャプション側の取り違えを検出。
3. **投稿インベントリ**：媒体（IG/X）・投稿ごとの抽出色番号数・対象商材カバレッジ。
4. `--demo-typo`：正解を1文字だけ書き換えた擬似ミスを混ぜ、機械照合が検出できることを実演。

いずれも **AIに正誤を判断させず、抽出した文字列を機械的に集合比較** しているだけ。だから「自信ありげな誤判定」が起きない、というのが設計の肝の実証です。

## 使い方

```bash
pip install -r requirements.txt
python3 cr_check.py <CRシート.pdf> [<CRシート.pdf> ...] [--demo-typo]
```

CRシートPDF（クライアント素材）は `.gitignore` によりリポジトリに含めません。手元のファイルパスを渡してください。

## 実装上わかった勘所（v1へ引き継ぐ）

- **対象商材欄は不完全なことが多い**（例：カバレッジ 5/15）。よって 指示⇔商材 の差分は「エラー」ではなく参考。照合は「指示 ∪ 商材」を正解側集合に使うのが安全。
- **色チャート/特集系の投稿は色番号が対象商材欄にしか無い**（例：シアーカラー一覧、ゼリー、世界の海）。指示欄だけを見ると取りこぼす。
- **X投稿はキャプションのみ（IG転載）**。照合対象の色番号がシート側に無いため、自動的にスキップ（IG側と突き合わせる案はv1で検討）。
- **表記ゆれは実在**（`＋`↔`+`、スペース有無、`・`↔`▶`）。正規化必須だが、色番号そのものの1文字差は絶対に吸収しない。

## v1（提出画像のOCR照合）— `ocr_match.py`

提出クリエイティブ画像をOCR（tesseract 日本語＋英語）で文字化し、CRシート由来の
「正解」色番号セットと機械照合する。設計どおり **OCRは「読む」だけ、一致判定は機械** が行う。

```bash
sudo apt-get install -y tesseract-ocr tesseract-ocr-jpn   # システム依存
pip install -r requirements.txt
python3 ocr_match.py <画像> --truth BL920,BL921,WT045R [--require "SPF50+,PA++++"] [--show-ocr]
```

### 実装のポイント：OCRノイズの選別（確信度）

OCRは同じ文字を別のパスで誤読することがある（例：`WT045R` を `TO045R` と読む）。
これを取り違えと誤検知しないよう、**複数パスでの検出回数と確信度**を持たせ、
低確信・単発の読みは「参考（除外）」に落とす。これにより：

- OCRノイズ `TO045R`（conf17・1回）→ 自動で除外
- 本物の取り違え `BL921`（conf92・6回）→ 高確信の指摘として提示

### 検証結果（`sample_output_v1.txt`）

レンダリング生成した「青背景＋白文字」のネイル風テスト画像（`BL920`〜`WT017A`）で：

- **CASE A**：色番号 **5/5 完全一致**、必須文字列 `SPF50+` / `PA++++` も検出。ノイズは除外。
- **CASE B**：正解を `BL921→BL922` に変えると、**`BL921` を高確信の取り違え疑い**として検出、`BL922` を未検出として提示。

→ v1の核心（**OCRで色番号を読み、1文字差を機械照合で捕まえる**）が、実際のOCRエンジンで成立することを確認。

> 注意：上記テスト画像は**クリーンなフォントでレンダリングした楽観ケース**です。実際の提出クリエイティブ（装飾フォント・写真の上の細い白文字）はより難しく、そこがまさに設計書でいう「Phase 1の重点検証」。**実物のネイルホリック提出画像（ファイル）**を頂ければ、現実の読み取り精度を実測します。

## まだやらないこと（次段階）

- 見切れ・コントラスト・文字サイズの画像側チェック（座標・色解析）。
- 正解ソース（Gスライド原本／スプレッドシート／コメント青字／Slack指示）の直接取り込みと、FIX/修正版の自動判別。
- キャプションの per-ambassador（@ハンドル単位）照合による、より細かい取り違え検出。
- 色番号だけでなく色ライン名・素材名（`ラメフレークカラーズ` 等）の画像側照合。
