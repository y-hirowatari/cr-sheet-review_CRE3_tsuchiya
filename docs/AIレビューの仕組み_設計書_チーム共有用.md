# AIレビューの仕組み（設計書・チーム共有用）｜ネイルホリック

※初版のたたき台です。検証の進捗に合わせて更新します。

-----

## このドキュメントについて

  - 対象読者：制作チームのリーダー・マネージャー
  - 目的：このAIレビューが**裏でどういう仕組みで動くのか**を理解してもらうこと。
  - 位置づけ：実装担当向けの技術仕様書（データ形式や閾値）や、クリエイター向けの操作説明とは別。ここでは「考え方」を共有します。
  - 前提：ネイルホリック案件を題材にしています。ただし仕組み自体は他案件にも横展開できる設計です。

-----

## 全体像（ひとことで）

クリエイターが専用アプリに提出物をアップロードすると、**CRシートを「正解」として機械的に突き合わせ**、客観的なミスを一次チェックします。クリエイターはその指摘を自分で直してから、これまで通りリーダーへレビュー依頼を出します。

リーダーは、主観（余白・トーン）の判断と最終OKを担います。AIはレビューを置き換えるのではなく、リーダーが受け取る提出物をきれいにする前さばきです。

ネイルホリックでこの仕組みが特に効くのは、**素材名・色番号・色名の取り違え**という、この案件で繰り返し起きてきた事故を、出稿前に機械的につぶせるからです。

-----

## なぜネイルホリックで、この仕組みなのか（案件の特性）

ネイルホリックには、AIレビューの設計に直結する特性があります。

  - **商材が非常に多い**：ネイル商材が大量にあり、色番号・色名・使用アイテムの種類が多い。人の目だけでは取り違えを見つけきれない。
  - **複製はしないルール**：毎回イチから作るため、過去物からの流用でミスを回避できない。文字を扱う回数が多く、打ち間違い・取り違えが構造的に発生しやすい。
  - **トンマナ資料（デザインレギュレーション）が無い**：戦略設計がなく、過去踏襲で受注してきた経緯があるため、明文化された「正解の配色・トンマナ」が存在しない。→ 配色チェックは「正解」を持てないので、参考レベルにとどめる（後述）。
  - **アート系素材のみ選定ルールがある**：Adobeストックのプランナー指定素材、または美術サイトのパブリックドメイン素材（商用OK）に限る、というルールが存在する。→ ルール順守の観点として扱う。
  - **CRシートの形式・修正の運用がばらつく**：基本はGスライド、回によってはスプレッドシート。修正指示はスライドのコメント（青字）だったり、Slackのテキストだったりする。→ 「正解ソースをどう確定するか」が運用上の肝になる（後述）。

つまりネイルホリックは「**明文化されたルールは少ないが、事実の取り違えリスクは高い**」案件です。だからこそ、AIには主観判断をさせず、**事実の照合**に徹させる設計が合っています。

-----

## 裏で何が起きているか

アップロードから最終OKまでの流れはこうです。

```
クリエイターがアプリにアップロード（案件を選択＋画像をページ順に）
        │
        ▼
AIが2つの情報源を読む ──┬── CRシート（文字データ＝正確に取得）
        │               └── 提出物（画像なのでOCRで文字抽出）
        ▼
機械的に突き合わせ → 客観項目を判定（証拠つき）
        │
        ▼
クリエイターが指摘を手で直す → 再チェック → 客観OK
        │
        ▼
リーダーへ連絡（AIの結果・証拠・直した点も同梱）
        │
        ▼
リーダーが主観を判断＋AIを検証 → 最終OK
```

ポイントは、AIが読む情報源が2つあることです。

  - **CRシート**：Googleスライド上の文字は「文字データ」として乗っているので、画像から読み取る必要がなく、そのまま正確に取れます。これを「正解」として扱います。色番号・色名・素材名も、ここから正確に取得します。
  - **提出物**：こちらは完成した画像なので、OCR（画像から文字を読み取る技術）で文字を抜き出します。

この2つを文字単位で突き合わせ、ズレを見つけます。

-----

## 設計の肝：なぜ「機械的に突き合わせる」のか

ここが今回いちばん大事な設計判断です。

以前、Geminiにアウトプットとクリエイティブシートを比較させて「問題なし」と出たのに、実際は中身が取り違えられていた、というインシデントがありました。原因は、AIに「これは正しい?」と**判断を任せた**ことです。AIは画像の印象から正誤を判断しようとすると、自信ありげに間違えます。

ネイルホリックでこれをやると、**「BE300」と「BE308」のような色番号の一字違いを、AIが「合っています」と自信満々に見逃す**という、最悪のパターンが起きます。

なので今回は、AIの仕事を**「文字を読み取る」ところまで**に限定します。読み取った文字が正解（CRシート）と合っているかどうかは、AIの判断ではなく**機械が文字単位で比較**して決めます。

「判断」ではなく「照合」。だから、自信ありげな誤判定が起きにくくなります。

色番号・色名・素材名の取り違えのような事実の間違いも、画像どうしの印象比較ではなく、CRシートの文字との照合で捕まえます。

-----

## なぜソース側は信頼できるのか（情報源の非対称性）

CRシートのテキストは文字データなので、誤りなく取れます。間違いが混じり得るのは提出物側のOCRだけです。

つまり、検証で気にすべきは「OCRがちゃんと読めているか」の一点に絞れます。たとえば写真の上の白文字や、装飾の強いフォント、細い色番号表記でうまく読み取れるか――そこさえ確認すれば、照合そのものは信頼できる、という構造になっています。

> ネイルホリック特有の注意：**色番号は短くて似た文字列が多い**（BE300 / BE308 など）ため、OCRの1文字の読み違いが致命的になり得ます。ここはPhase 1の重点検証ポイントです。

-----

## ネイルホリック特有の論点：「正解ソースをどう確定するか」

一般的な案件と違い、ネイルホリックはCRシートの形式と修正の運用がばらつきます。

  - CRシート本体：基本はGスライド、回によってはスプレッドシート。
  - 修正指示：スライドのコメント（青字）に書かれることもあれば、Slackのテキストで来ることもある。

照合の「正解」は、**本体の指定＋最新の修正指示を反映したもの**であるべきです。ここが混ざると、「古い色番号と照合してしまう」「Slackで来た修正が正解に反映されていない」といった取りこぼしが起きます。

そのため運用として、

  - アップロード時に**どのCRシート（および最新の修正スレッド）が正解か**をクリエイターが明示する、
  - スライドのコメント（青字）やSlack指示は、照合前に正解テキストへ反映されている前提を明確にする、

という段取りを置きます。ツール側でどこまで自動吸収できるか（コメントの取り込み等）は検証しながら詰めます。

## 配色チェックの割り切り（トンマナ資料が無いこと）

ネイルホリックには明文化されたトンマナ／デザインレギュレーションがありません。したがって、配色チェックには**「これが正解」と言える基準が存在しません。**

  - v1では、配色は「ブランドカラーから大きく外れていないか」の**参考レベルの気づき**にとどめます。NG判定の根拠にはしません。
  - 将来的には、過去の投稿からブランドの使用カラー傾向を抽出して参考パレットを作る、といった補強は検討可能です。ただし「過去踏襲」であって「正解」ではない点は共有しておきます。

これは正直に線を引いておくべきところです。**配色でAIがNGを出しても、それは基準に基づく判定ではなく参考**だと、リーダー・クリエイター双方が理解している必要があります。

-----

## アート系素材の選定ルールの扱い

ネイルホリックには、アート系素材の引用ルールがあります。

  1.  Adobeストックから、プランナーが選定した指定素材を使う。
  2.  美術サイトでパブリックドメインと明記されたもの（商用OK）を使う。

このルールは「画像を見れば機械的に判定できる」種類のものではありません（出典・許諾はメタ情報に依存するため）。したがって、

  - v1では、AIは**「アート系素材を使っているように見える場合は、出典がルールに沿っているか確認を促す」チェックリスト提示**にとどめます。出典そのものの正誤判定はしません。
  - 出典の確認は、クリエイターの自己申告＋リーダーの確認で担保します。

-----

## なぜクリエイターが主役でも、リーダーのゲートを残すのか

このフローでは、クリエイターが自分でチェックして修正してから連絡してきます。それでもリーダーのレビューは残します。理由は2つ。

  - AIが見るのは**客観的なミスだけ**で、デザインの質（余白・トーン・全体の良し悪し）は人の判断が要るから。
  - AIは間違えることがあるから。クリエイターのセルフチェックは「最初のチェック」であって、合格判定ではありません。

-----

## リーダーへ連絡するとき、AIの結果も同梱する

クリエイターがリーダーへ連絡する際、最終提出物だけでなく、**AIチェックの結果（指摘内容・証拠・直した点）**も一緒に渡します。これには3つの意味があります。

1.  **ゲートが甘くならない**：完成品だけが出てくると、「AIがOKならいいか」とつい通してしまう（取り違えの時と同じ）。指摘と証拠が添えてあれば、リーダーは「何をチェック済みで、どこを直したか」を見たうえで判断できます。
2.  **精度データが貯まる**：リーダーが「AIが見逃した／誤検知した」を記録できるので、どの項目が信頼できるか見極められます。ネイルホリックでは特に「色番号OCRの精度」がここで見えてきます。
3.  **クリエイターが思い込まない**：AIのOKを「完成」と捉えず、最後は人の目を通る前提が共有されます。

-----

## 行動面で気をつけること

クリエイターが主役になる分、AIの出力が「合格通知」に見えると、本人の見直しが止まってしまいます。これがこの流れでいちばん注意したいリスクです。

なので、AIの結果は**「直してほしい点の一覧」**として見せ、「合格」とは言わせません。クリエイター向け資料に入れた「AIは間違える、最終確認は自分の目で」「色番号・色名・素材名は手打ちせずコピペ」が、この流れでは一段と重要になります。

-----

## AIが見る / 見ない の線引き

|  | **内容** | **担当** |
| :- | :- | :- |
| **見る（客観）** | 文言の一致／**色番号・色名・素材名の一致**／必須要素（CTA・ロゴ・注釈・価格・発売日）／表紙の見切れ／コントラスト（読みやすさ）／文字サイズ | AIが一次チェック |
| **見る（参考）** | 配色（ブランドカラーからの逸脱）／アート系素材の出典ルール確認の促し | AIは気づきの提示のみ・判定はしない |
| **見ない（主観）** | 余白感、全体のトーン、エモさ、デザインとしての良し悪し | リーダーが判断 |

ざっくり言えば、AIは「読みやすさ」と「間違い探し（特に色番号・色名・素材名）」担当、リーダーは「デザインの質」担当です。

-----

## リーダーの役割（最終ゲート）

  - AIは一次チェックであって、最終判定者ではありません。**最終OKは必ず人が出します。**
  - 連絡時に同梱されたAIの指摘には**証拠**が付きます（例：「3枚目の色番号が『BE308』だが、CRシート指定は『BE300』」「表紙の白文字のコントラストが2.8、基準は4.5」）。なので「AIがNGと言ったから」ではなく、**証拠を見て数秒で正誤を判断**できます。
  - 余白やトーンといった感覚的な部分の判断は、これまで通りリーダーが担います。ここがレビューの価値の中心であり、AIに任せない部分です。

AIが客観的な前さばきを済ませることで、リーダーはデザインの中身に集中できる――というのが全体のねらいです。

-----

## いまできること / まだできないこと（正直に）

**できること**

  - 客観項目の一次チェック（文言／色番号・色名・素材名／必須要素／見切れ／コントラスト／文字サイズ）
  - 証拠付きの指摘一覧と、正しい文言・色番号（コピペ用）の提示
  - リーダーへの引き渡しバンドル（提出物＋AI結果＋直した点）

**v1での割り切り**

  - 修正の反映は**クリエイターの手**で行います。AIは「直すべき点と正しい文言・色番号」を提示するところまで。AIが提出物を直接書き換えることはしません（編集データとレイアウトを守るため）。
  - 配色は参考レベル（トンマナ資料が無いため、NG判定の根拠にしない）。
  - アート系素材の出典ルールは、確認の促しにとどめる（出典の正誤判定はしない）。

**まだできない・検証中のこと**

  - 装飾フォントや写真上の白文字、細い色番号表記のOCR精度（Phase 1の重点検証ポイント）
  - CRシートの形式ばらつき（Gスライド／スプレッドシート）と、修正指示（スライドのコメント青字／Slack）の正解ソース自動吸収
  - 指摘を反映した自動修正・編集可能データの出力（Figma／Claude Designとの連携で今後検証）
  - 配色の参考パレット化（過去投稿からのブランドカラー傾向抽出）

-----

## 導入の段取り

  - **Phase 1**：ネイルホリックで試します。クリエイターがアプリで自己チェック → 自分で修正 → リーダーへ連絡、という流れを回します。まずは**色番号・色名・素材名の照合**と**文言照合**に絞り、最も事故の多いポイントで効果を検証します。
  - **慣らし運転**：最初の1〜2週間は、リーダーが受け取った提出物について、同梱されたAI結果と自分の判断の差分を記録します。特に色番号OCRの拾い漏れ・誤検知の傾向をためて、信頼できる項目から運用を固めます。
  - **その後**：正解ソース（CRシート形式・修正指示）の自動吸収 → 自動修正（編集可能データ出力）→ 納期リマインドの自動化、と広げていきます。

-----

## リーダーのみなさんへのお願い

1.  慣らし運転の期間、**同梱されたAIの結果と自分の判断の差分**を記録・共有してください。どの項目が信頼できるかを見極めるために使います。特に「色番号・色名・素材名のOCRが正しく読めていたか」を重点的に見てください。
2.  「実機で見て問題ない最小文字サイズ」「読みづらいと感じるコントラストの実例」を、いくつか共有してください。基準値をネイルホリックの感覚に合わせて確定するために使います。
3.  配色について、「これはブランドとして明らかに外れ」と言える実例があれば共有してください。トンマナ資料が無い中で、参考パレットを作る手がかりにします。
